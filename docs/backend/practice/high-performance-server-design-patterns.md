# 高并发场景的常用设计方案

公司经常承接一些市级活动，在完成任务的同时也积累了很多高并发的解决方案，一下场景是目前公司常用到的一些技术方案。

## 高读场景的几种处理方式

### 1. 借用对象存储、CDN能力

所有接口获取信息的接口返回的内容可以理解为一个JSON文件，那么这个json文件就可以通过后端进行预生成，在编辑在后台操作的时候（增、删、改）进行相关接口的JSON文件生成，同时将生成的文件上传至云对象存储中（公司目前为七牛云），通过将接口内容上传至云厂商里，那么C端所有的访问流量全部走到云厂商的云存储以及CDN中，自己系统的访问量只有后台编辑以及一些非高频访问接口，例如：资讯流列表接口的第二页。当然也可以不用对象存储，直接对接口地址做CDN加速，此时注意不能有签名，不然会导致CDN加速失效。

优点：并发量可以说能达到十万级，并发量不会击穿到自有系统。

缺点：目前很多CDN厂商对于接口的刷新次数有限制，需进行商务沟通。

### 2. 使用redis建立数据缓存
高度场景，系统并发瓶颈基本在数据库，那么这个时候可以让C端高并发接口只读redis数据，然后直接返回。为了避免流量击穿，那么redis的key生命周期应该是永远有效，同时利用job进行定时更新各key的缓存内容。通过这种处理方式既能实现高并发也能实现数据的近实时更新。

优点：此方式能够一定程度上提高系统并发能，不需借用三方厂商能力，数据刷新频率自主可控。

缺点：

1、并发能力还是依托于代码质量以及服务器硬件配置

2、带宽要求比较高

## 高写场景
### 1. 报名场景（无名额限制）
该场景目前公司涉及的活动主要有数字人民币报名。系统设计模式运用了前后运算解耦操作，将复杂运算后移至后台异步处理，保障C端请求能够快速响应从而提升整个系统的并发能力。

### 2. 抢购场景（异步处理、有名额限制）
该场景在2.1的基础上多了一个名额限制，那么在系统架构上的难点就是在高并发的基础上如何防止超发。此场景中引入了redis中间件来实现计数以及锁功能。具体新增控制项如下：
- 1. 前端接口在收到请求后判断活动状态（开始、进行中、结束）、库存状态（获取redis中可发总数以及已发数量，两数相减获取剩余库存）
- 2. 在消费者代码中获取redis中可发总数以及已发数量，两数相减获取剩余库存，此处需判断是否加入redis锁，条件为系统的消费者数量，若消费者数量为20，那么当剩余库存<=20时将加入redis锁进行库存扣减单进程控制。

### 3. 抢购场景（同步处理、有名额限制）
对于一些并发要求不是很高的场景可以使用同步操作来实现，那么为了尽可能同步系统并发能力，那么就需要将数据库的库存扣除操作转入redis。具体核心控制项如下：
- 1. 前端接口在收到请求后判断活动状态（开始、进行中、结束）、库存状态（获取redis中可发总数以及已发数量，两数相减获取剩余库存），此处的需引用redis悲观锁来控制库存超发，条件为当库存高于预估并发时不做锁操作，当库存<=并发阈值时加入redis悲观锁，通过适时的引入悲观锁既保障了并发效率也能在最后临近库存清空时保障库存不超发。
- 2. 为了保障系统的并发能力，避免mysql的同行自增或自减操作，那所有库存操作均在redis中，那么剩余库存（已发数量）需通过job定时回填至数据库，减少数据库的产生行锁影响系统并发能力。

## 4. 总结
从以上描述可以看到， 对于提升并发能力主要是在减少数据库的操作，引入CDN或redis来进行数据缓存，避免数据库的频繁读写从而提升系统的读取性能。对于高写操作，主要引用队列进行流量隔离，避免大访问量直接操作数据库，而是通过系统的消费者数量来控制数据库的读写量，保证了系统在高并发时的健壮性也能优化C端的体验性，减少用户看到“系统繁忙”。
